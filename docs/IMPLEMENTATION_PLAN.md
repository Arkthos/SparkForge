# Implementation plan

This publication preserves the owner's spec-driven factory objective and the
implemented operator-assisted slice. It does not import private platform policy,
execution history or unperformed acceptance. The CSV [backlog](IMPLEMENTATION_BACKLOG.csv)
owns dependency/status details; the [requirements](PRODUCT_REQUIREMENTS.md),
[contracts](design/CONTRACTS.md) and [test strategy](engineering/TEST_STRATEGY.md)
own their respective semantics.

The local product goal is WP-080. Repository publication under WP-002 is
administrative distribution of cleared project material, not proof of that
product goal, platform contribution or deployment.

## P0: baseline and publication

### WP-000: engineering baseline

Maintain a coherent requirement, contract, decision, test, source and work
inventory with explicit unknowns. Validate links/dependencies/lifecycle without
claiming a documentation pass is product acceptance.

### WP-001: owner-directed scope

Record the requested product and bounded development/publication scope.
Separate that direction from actual real-job approval, live resources and
private-source disclosure rights.

### WP-002: clean private repository publication

Publish owned code, synthetic tests, source-neutral docs and reviewed public
research in a fresh history. Keep restricted originals and operational state
outside. Validate the complete outgoing tree/history and exact private remote
commit, not only a selected diff or successful shell exit.

## P1: actual host and control feasibility

### WP-010: selected host

Obtain the real operator-approved host/build/profile and qualification scope.
Do not substitute an available executable, another account or a package label.

### WP-011: interface inventory

Inspect the authorized selected host's actual supported package, tool,
permission, completion and stop interfaces. Distinguish documentation,
metadata observations and qualified behavior.

### WP-012: execution envelope

Approve source/provider/storage/retention, tools, targets, limits and effects.
Begin with synthetic data; an existing directory or credential is not authority.

### WP-013: trusted boundary qualification

Use specifically permitted disposable probes to establish actual identity,
approval, effect, acceptance, isolation and recovery controls. If enforcement
is missing, retain a narrower assisted scope rather than invent a guarantee.

### WP-014: implementation commitment

Choose supported mechanisms from evidence and maintainability. Reuse existing
code where its contract/side effects fit; unresolved critical decisions stay open.

### WP-015: host-record checker

Retain the implemented standard-library consistency checker, synthetic inputs
and refusal cases. Valid records never become host/execution permission.

### WP-016: disposable storage probes

Retain the bounded owned-file/process observations and conservative cleanup.
Replacement/conflict/interruption tests are not production-store, synchronization
or power-loss qualification.

### WP-017: offline UX preview

Maintain the fictional intent/fit/brief/template/feedback flow with tab-local
state. No real comparison, AI execution or durable approval is inferred.

### WP-018: preview evidence

Exercise the actual copied assets and record model, asset and browser scopes
separately. Do not relabel an old receipt or synthetic user as fresh acceptance.

## P2: reusable implementation and remaining foundation

WP-026 already implements a narrower subset of the following target mechanisms.
Inspect and reuse it before extending anything; do not rebuild completed logic.

### WP-020: qualified package foundation

Qualify or adapt the minimal owned package to the selected host, without
undeclared root/sibling dependencies or unapproved installation/registration.

### WP-021: versioned contracts

Extend the executable schemas only as needed for the target C-001..C-016
obligations. Unknown versions, fields and conflicting scope fail explicitly.

### WP-022: durable recorder

Build on transactional event/state/intent handling. Protect provenance and
reconstructible state; preserve conflicts, persistence failures and uncertainty.

### WP-023: trusted admission

Connect actual decision ingress, current permissions and resources to effect
admission. Worker-written JSON and actor strings do not supply this boundary.

### WP-024: workspace and process ownership

Inspect owned/dirty paths without resetting unrelated work. Bind candidate
files and track only owned operations; qualify actual confinement separately.

### WP-025: deterministic checks

Reuse exact-command execution, finite limits and complete-result admission.
Collect trustworthy binding/completion evidence; zero exit is insufficient.

### WP-026: local assisted native slice

Preserve the complete skill/agent workflow and the implemented snapshot/spec/
check/review mechanisms. Validate their synthetic cross-module behavior and
package portability without claiming actual environment acceptance.

### WP-027: exact-candidate self-use and review

Use the engineering harness only with its explicitly synthetic source/decision
fixtures. A changed publication candidate needs its own actual check/reviewer
context; private historical tokens and verdicts are not transferable.

## P3: guided intent and reuse

### WP-030: authorized knowledge integration

Reuse the snapshot adapter. Qualify any live connector and actual environment
permissions independently. Preserve denied/stale/partial coverage and cite
relevant implementation, not just component names.

### WP-031: intake and comparison

Clarify only consequential gaps and explain supported output/reuse/update/new
choices using actual authorized evidence. Unavailable comparison is visible.

### WP-032: exact behavior and decisions

Produce observable acceptance, non-goals and complete check/reviewer inventory.
Display the exact specification and honor accept/reject/revise without inference.

## P4: full engineering loop

### WP-040: scoped builders and test authors

Use host-approved work with bounded owned paths and meaningful tests.
No framework/provider fallback or permission expansion follows from failure.

### WP-041: complete independent barrier

Require current checks and all applicable independent reviewers. Seed negative
controls and protect criteria from candidate/learner changes.

### WP-042: bounded correction

Reproduce failures, repair accepted behavior, rerun affected checks and stop
at limits or no progress. Preserve failures and escalate changed intent.

### WP-043: representative end-to-end integration

Exercise authorized new/brownfield journeys, including real failure and repair.
Fixture integration does not replace a real selected-host model/user journey.

## P5: feedback, recovery and governed learning

### WP-050: readable feedback and state

Explain current evidence, blockers and revisions without granting authority.
Route feedback to in-scope repair or renewed intent approval.

### WP-051: recovery and reconciliation

Preserve intent before dispatch and reconcile unknown effects before retry.
Do not restart inference or writes merely because a session was interrupted.

### WP-052: optional concurrency

Keep serial operation valid. Add concurrent support only after actual isolation,
ownership and capacity qualification; do not infer it from worktrees.

### WP-053: inactive learning proposals

Use permitted observations with source/role/revision provenance and a falsifiable
hypothesis. Explicit no-change and inert follow-ups are valid outcomes.

### WP-054: independent promotion lifecycle

Evaluate baseline/candidate and mandatory regressions under protected criteria.
Require exact independent promotion, monitoring and safe authorized withdrawal.
Do not let the learner change policy, evaluator, permissions or budget.

## P6: actual qualification

### WP-060: maintained user/operator guidance

Keep examples, troubleshooting and support claims tied to actual implemented
behavior and current evidence. Unqualified commands remain clearly labeled.

### WP-061: installed lifecycle

Qualify fresh discovery, install, upgrade, interruption and uninstall on the
selected host without shadow checkout/cache dependencies or unrelated deletion.

### WP-062: contribution effect boundary

Prepare exact local deltas and test rejection of missing/stale/changed effect
authorization. Actual external submission remains a separate operation.

### WP-070: real environment journeys

Run approved representative new/brownfield/learning tasks on the selected
installed source. Record actual outcomes, limits and genuine human decisions.

### WP-071: independent negative/recovery qualification

Exercise scoped fault, privacy, source, evidence and learning boundaries.
No critical unknown effect or accepted bad control may be hidden.

### WP-072: domain-user acceptance

Use real participants and an independently accepted rubric. Explain support,
approvals, failures and feedback from documentation rather than private chat.

## P7: local consideration and separate external decisions

### WP-080: coherent consideration package

Assemble exact tested artifacts, cleared evidence, guides, terms and genuine
stage-appropriate ownership. Local readiness is not received acceptance.

### WP-081: separately authorized platform submission

Execute only the approved target/payload/effect and verify its actual outcome.
Publishing this development repository does not submit a platform contribution.

### WP-082: actual reviewer feedback

Record real received findings/decisions and scoped rework. Changed acceptance
or intent needs renewed decisions and applicable evidence.

## P8: independent later adaptation

### WP-090: cleared transfer

Transfer only the specifically permitted code/docs/evidence subset.
No credentials, runtime state, private source capture or unapproved learning
crosses environments merely because a package can be built.

### WP-091: target-local adaptation

Use target-approved host/data/packaging/integration choices. Keep credentials,
state and knowledge boundaries independent and use only shipped resources.

### WP-092: target-local qualification

Establish fresh target-specific install, workflow, recovery and learning
acceptance. Another environment's green result is comparison, not permission
or proof of compatibility.

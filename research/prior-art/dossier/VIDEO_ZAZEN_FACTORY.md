## Why this example is useful

The walkthrough complements the [Risco review](../../ai-factory/20-eric-risco-video-review.md):
it shows a factory being built and then modified after workflow friction,
rather than only presenting a finished diagram.

The transferable foundation is a small comprehensible structure: a job,
explicit artifacts, owned responsibilities, a complete review barrier, visible
state, and a route back to a person. Understanding those contracts matters
more than installing a large fashionable framework.

A screenshot-only interpretation misses a key evolution: **worktrees are
added during the video**. The overview's "next steps" belongs to an earlier
point, not necessarily the final state. The later v1 README explicitly
distinguishes the original shared `board.json` prompt from per-job
`job.json` state.

The public review is conceptual and workflow prior art, not a ready package
or authority to replace the project's accepted-brief, selected-host, reuse,
or delivery requirements. Private integration comparisons from the original
document are not reproduced.

## Artifacts as interfaces

The [current v1 skill](EVIDENCE.md#zazen-orchestrator) and
[role contracts](EVIDENCE.md#zazen-spec-writer) divide work into inspectable
artifacts:

| Intended owner | Artifact or effect | Useful boundary |
|---|---|---|
| Orchestrating session | Job's `job.json` | One intended state writer per job |
| Specification writer | `spec.md` | Context, requirements, observable acceptance, non-goals, assumptions |
| Builder | Job-branch commits and `build.md` | Implementation evidence separate from the specification |
| Each reviewer | Its own `round-N/review-*.md` | Independent finding/verdict files rather than interleaved chat |
| Model approver | `decision.md` | Consolidated readiness/risk explanation separate from individual reviews |
| User-directed rework | Saved rework note | Attributable feedback instead of lost conversation |
| Dashboard | Reads job/report state | Presentation, not the authority that makes the result correct |

A domain expert can inspect a brief, unresolved decision, finding, or evidence
summary without reading the entire model transcript. But single-writer
instructions do not prove exclusive leases, atomic updates, protected
acceptance, or tamper resistance. The demonstration's bypass mode makes it
especially inappropriate to treat those role rules as an OS permission
boundary.

## Complete review rounds and the exact correction limit

The current v1 skill waits for every required reviewer file in the current
round, reads the expected verdict header, and stops when a reviewer produces
no file or an invalid verdict.

The useful mechanism is the barrier. Resuming the builder when the first
review requests changes, while other reviewers still inspect the old revision,
would make their findings refer to different moving targets.

The [declared policy](EVIDENCE.md#zazen-orchestrator) is `MAX_RESUMES = 2`:
two builder resumptions after the first round, hence **at most three review
rounds** for that invocation. The overview's shorter "max 2" label should not
be assumed to mean two total rounds.

User-directed rework receives a fresh allowance. This is not an enforced
lifetime cost budget for the job, and neither limit was runtime-tested by the
review. A product must define how cumulative usage and repeated rework are
accounted for rather than inherit an allowance reset as unlimited authority.

The required review set should fit the component. A page may need UI/UX
assessment; a query, nonvisual skill, or adapter needs different domain and
contract checks. Four named reviewers do not provide four independent
proofs of correctness.

## State and workspaces evolve

The [original prompt](EVIDENCE.md#zazen-build-prompt) uses a shared
`factory/board.json`. The [later v1 README](EVIDENCE.md#zazen-factory-overview)
explicitly calls that prompt historical and describes per-job `job.json`.

The current skill assigns separate worktrees/branches, ports, and browser
session names. Job metadata lives outside the temporary code worktree so it
can still be inspected after integration. Absolute paths and a branch check
reduce wrong-workspace mistakes when every shell call starts fresh.

These are separation principles, not credential, filesystem, or network
isolation. Bash commands, Claude tools, role naming, and `SendMessage`
semantics need adaptation to another host; Markdown files alone do not make
them portable.

Persistent files and live agent memory are different:

- The demonstration shows a later human decision from another session using
  files.
- The automatic fix loop resumes a named live builder.
- The v1 rework contract can launch a fresh builder from earlier files.
- General crash recovery, uncertain external effects, and automatic session
  reconstruction were not demonstrated or tested by this review.

## What can be reused as a concept

| Retain | Qualification required for an adoption |
|---|---|
| A small comprehensible process | Prompt-driven transitions are not necessarily enforced transitions |
| Read existing repository instructions and code | Also perform an authorized current reuse comparison; missing coverage is not absence |
| Observable criteria and non-goals | Obtain the required pre-code decision rather than defer consequential assumptions to the final approver |
| Named inspectable artifacts | Bind criteria, tests, and reviews to job/spec/code revision |
| Full review barrier and bounded corrections | Distinguish missing, stale, invalid, failed, and timed-out evidence |
| Separate worktree/ports/browser identity | Qualify real host isolation and process ownership; do not inherit bypass mode |
| `STATUS: BLOCKED` with explanations | Distinguish intent decisions, unavailable access, environment faults, defects, and integration conflicts |
| Dashboard visibility | Derive status from evidence; moving a card or writing PASS is not proof |
| Runtime state excluded from normal source commits | Provide authorized retention/recovery; ignored files do not survive a fresh clone by themselves |
| Actual repository checks and explicit-path staging | Keep meaningful test-writing capability; absence of an existing runner is not permission to waive behavior checks |

The [builder contract](EVIDENCE.md#zazen-builder) asks for evidence per
criterion, actual repository commands, explicit-path staging, preserved round
history, and no repository-wide formatting changes. The
[code-reviewer contract](EVIDENCE.md#zazen-code-reviewer) reads current
diff/prior findings, reruns checks, cites files/lines, and separates defects
from style notes. These are valuable procedures, not evidence of perfect
model compliance.

## Approval and delivery must not be conflated

The initial overview's general guidance includes specification approval and
human-reviewed PRs. The demonstrated v1 path moves from a generated spec to
building, and its [approver contract](EVIDENCE.md#zazen-approver) lets a model
`APPROVE` authorize local-main integration.

V1 merges **locally into `main` and explicitly says never to push**. That is
not evidence of automatic production deployment. It is still a different
authority model from a product that requires accepted intent before coding
and a separately authorized integration decision.

Keep requester intent, automated readiness assessment, and external
submission/acceptance distinct. A model can propose or classify but cannot
manufacture the other authorities. A model-generated backlog is not
permission to begin work.

## Separate v2 follow-up and licensing

The [v2 README](EVIDENCE.md#zazen-v2-overview) documents issue intake,
conditional reviewers, per-job state, concurrency, a script-backed state
writer, a real-check gate before review, PR delivery, recovery claims, and
checks after base synchronization. These are useful responses to v1
limitations.

Only the README and opening license text were reviewed, **not executable
implementation**. It still describes model-authorized PR merging. Using a
PR endpoint alone does not prove that another product's required approvals
are preserved.

No standard root/v1 license was established from selected material, although
the v1 README invites copying. V2 includes a scoped
[GPLv3 license](EVIDENCE.md#zazen-v2-license). GPL permits commercial use
subject to its conditions; it is not noncommercial-only. An offered separate
commercial license does not change that distinction. The v2 grant must not
be generalized to sibling directories.
